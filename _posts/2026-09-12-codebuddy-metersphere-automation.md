测试资产自动化，不是买一个平台，而是把工作方法本身变成能执行的 skill。我们手上有两个旧 skill：CodeBuddy 里的 testbuddy 负责用例设计，metersphere 查询包负责数据查询与接口用例，中间全靠人脑衔接。用大模型把它们融成一个 testerbuddy 后，需求分析、用例生成、评审跟踪串成了一条链路，每道工序还带着门禁。改造旧 skill 比从零新建便宜得多，这篇文章就是我们怎么改的。

## 改造前：两个 skill 各管一摊，靠人脑做胶水

testbuddy 和 metersphere 各自都能跑，但边界是断的：testbuddy 懂用例设计不懂 MeterSphere 数据，metersphere 懂查询不懂用例该长什么样。ms_client 的调用逻辑在 design 和 case-decay 里各存一份同源副本，改一处忘另一处是常态。

胶水只能靠人：什么时候调哪个脚本、生成后要不要过评审、删之前要不要确认，都写在人脑里。skill 文档写的是"怎么用"，没写"什么时候用"和"用了之后要守住什么"。

## 第一步：顶层 SKILL.md 只做意图路由，不写实现

改造的第一件事不是写代码，是画一张路由表。顶层 SKILL.md 只做两件事：把用户意图指到正确的子件，把全局纪律钉在每个子件头上。

| 用户意图 | 子件 |
| --- | --- |
| 生成测试设计/用例/框架；把需求落到 MeterSphere | tester-design |
| 用例腐化/治理/整改/清理 | tester-case-decay |
| 记录/查询代码与用例的关联 | tester-code-case-link |

路由表之外，全局纪律写死：证据边界（只吃需求文本和本地文件）、零猜测（缺口挂 `gap_ref` 标注待澄清）、变更先 `--dry-run`、删除必须显式 `--yes`。这些纪律在三个子件里同时生效，不用重复粘贴。

## 需求分析这道工序：先审计，再生成

需求进来先过 QA 审计：模块化解构 + 审计三清单（歧义/矛盾/缺失）+ P0-P2 分级。审计不是走过场，缺的 actor、前置条件、失败路径直接写进澄清清单，禁止编造。这是整个链路的地基，地基里没有幻觉，后面才能谈自动化。

## 用例生成这道工序：Cockburn 建模，9 道门禁放行

审计通过后，生成器把需求变成四层设计树：FEATURE 建一级模块，SCENE 建二级模块，TEST_POINT 只做用例名前缀，CASE 落成功能用例。用例长得像这样：

```json
{
  "nodes": [
    { "uid": "s1", "name": "结算主流程", "kind": "SCENE", "parent_uid": "f1" },
    { "uid": "case1", "name": "叠加多张券取最优", "kind": "CASE", "parent_uid": "c1",
      "instance": {
        "preconditions": "已登录且购物车含可结算商品",
        "priority": "P1",
        "steps": [
          { "action": "用户提交结算，携带多张可用优惠券", "expected": "系统选择最优抵扣并返回应付金额" }
        ]
      }
    }
  ]
}
```

步骤只写"用户意图 + 系统响应"，禁止 UI 点击细节。落库前过 9 项质量门禁，阻塞项不补齐不许落库：

```text
# 9 项门禁（references/qa/quality-gate.md）
# Scope 明确 / Sea-Level / 前置条件可测 / MSS 主动主谓宾（无 UI 细节）
# 成功保证可验证 / 最小保证 / 扩展编码 / 证据边界 / 无不可测定性词
```

落库本身也是一道门：先 `--dry-run` 出清单，人确认后正式写。

```bash
python <SKILL_DIR>/scripts/ms_design.py --design draft.json \
  --name 优惠券结算_20260912 --parent root --dry-run
```

接口用例走另一条线：Swagger/OpenAPI 导入生成接口定义与接口用例，和功能用例共用同一套落库管道。

## Cockburn 的设计理念被翻译成了 9 道门禁

quality-gate.md 的第一行就写着依据：Cockburn《Writing Effective Use Cases》与 QA Prompt 基线。它没把书抄进 README，而是把书里的概念逐条翻译成机器可检查的判定条件：

| 《Writing Effective Use Cases》的概念 | 在 skill 里的落地 |
| --- | --- |
| 用例高度体系，Sea-Level（用户目标级） | 门禁 2：不许掉到水下（UI 细节/内部实现），也不许飘到云端（战略层） |
| Scope（SuD，被讨论系统） | 门禁 1：系统边界明确且被尊重 |
| 前置条件 | 门禁 3：必须写成可测的事实陈述，而不是动作 |
| 主成功场景（MSS） | 门禁 4：意图 → 响应，主动主谓宾，无 UI 点击细节 |
| 成功保证 | 门禁 5：可验证的后置条件 |
| 最小保证 | 门禁 6：异常终止时系统至少交付什么 |
| 扩展（2a、2a1 编码） | 门禁 7：每条扩展显式编码，结束于重回 MSS 或终止 |

扩展的写法也沿用原书：`2a. 券已过期 → 2a1. 系统跳过该券并重算 → 重回步骤 3`。源文没定义的失败路径不编扩展，挂 `gap_ref` 进缺口清单——"写扩展"这件事本身也被纳入了证据边界。

最后两道门禁（证据边界、不可测定性词量化）是书外的补充：前 7 道保证"用例像 Cockburn 写的"，后 2 道保证"用例是我们要求的、不是模型编的"。

## 评审这道工序：状态可追踪，不再是黑盒

用例落库后，评审信息随查随有：评审单有哪些、每条用例是否参与过评审、当前状态是什么。状态机是明确的：

```text
UN_REVIEWED → UNDER_REVIEWED → PASS / UN_PASS
```

用例详情自动带上评审记录和缺陷关联，回答"哪些用例被评审过"不需要翻评审单，问一句就行。

## 计划与执行：资产备齐，执行交给平台

测试计划与执行这一环，skill 的边界是诚实的：用例 summary 里带测试计划数，评审状态可控，资产是"备齐可执行"的；到执行本身，创建计划、跑用例仍然在 MeterSphere 平台侧完成。自动化把前 80% 变稳了，剩下的 20% 留给平台和人。

## 改造实录里最有价值的产出：事故纪律

改造过程中最大的教训来自一次事故：2026-09-04，只读探测时对一个删除接口发了个 GET，结果 `GET /functional/case/module/delete/{id}` 收到 GET 就直接级联删掉整棵模块树，不进回收站。

这次事故被写进技能包随包分发，成了三条硬纪律：

1. 语义为删除/变更的接口禁止用 GET 探测，只靠已知只读接口和 405/404 区分。
2. 所有变更操作先 `--dry-run` 出清单，验证限定在沙箱模块。
3. 删除必须显式 `--yes`，非空模块拒绝删除。

纪律最后变成了代码：delete 脚本对非空模块直接拒绝，真想清空就降级为重命名加 `[空-待删除]` 前缀。

## 验收与收尾：改造完成的定义不是"能跑"

验收清单写得很具体：产出无内网插件残留与旧 CodeBuddy 插件内容，用 `rg` 扫描关键词；打包排除 `.env`，密钥不随包分发；同源副本（ms_client）两处同步。改造完成的定义是"干净、可分发、密钥不泄露"，不是"demo 能跑"。

## 结论：大模型负责合并与生成，人负责边界

整条链路的可信度，来自每道工序都有人工门禁：审计不给幻觉放行，门禁不给带病用例放行，dry-run 不给误删放行。大模型负责把旧 skill 的骨架和脚本合并出新的 testerbuddy，metersphere 负责把资产落到平台，纪律负责兜底。这套"意图路由 + 子件拆件 + 纪律注入 + 验收脱敏"的改造模式，可以平移到任何旧 skill 融合。
